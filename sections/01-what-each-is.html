What each thing actually is

Naming is misleading in this space: one option is an installer for something you cannot see, another is named for a platform it does not integrate with. This page states what is actually in each artifact.

SUNK — coreweave/sunk-anywhere

What is public

docs/, helm-values/, examples/ (6 validation scripts), infrastructure/ (provider patches), skills/ (agent playbooks), AGENTS.md, CLAUDE.md. No charts/, no operator/controller Go, no Dockerfiles, no CRD definitions.

Deploy model

You point an AI coding agent (Claude Code / Gemini / Cursor) at the repo and say "Deploy SUNK on EKS"; the agent reads a provider skill and drives helm/kubectl against the proprietary chart repo you were licensed.

What it ships when charts are available

SUNK operator + Slurm (controller, accounting, login, syncer, pod scheduler), cert-manager, MOCO MySQL (slurmdbd store), in-cluster NFS (/home), DCGM GPU monitoring, cloud dashboards, one default POSIX user. GPU node pool + LDAP/authentik + SkyPilot are opt-in.

[verified: repo tree + README Quick Start, HEAD ca81a7a3]

Slinky — SlinkyProject/slurm-operator + slurm-bridge

A real Kubernetes operator: CRDs (nodeset, loginset, accounting, restapi, token), controllers, and Helm charts all in-repo under Apache-2.0, published to ghcr.io. slurmctld runs as a pod. The companion slurm-bridge is a K8s scheduler that binds K8s workloads through the Slurm controller, which is what makes true gang/co-scheduling of mixed K8s+Slurm work possible.

On AWS, the official awslabs/ai-on-eks Slinky blueprint supplies the EFA layer the operator deliberately leaves out: the EFA device resource on the slurmd NodeSet and the aws-ofi-nccl stack copied from the AWS Deep Learning Container.

[verified: SlinkyProject/slurm-operator repo + slurm-bridge README + awslabs/ai-on-eks blueprint]

Ours — slurm-on-eks-hyperpod

A hand-written port of Google's GKE Slurm reference, built as plain StatefulSets/Deployments with headless-service DNS — no operator, no CRDs. Slurm 24.05.4 built from source. GPU via the device plugin; EFA configured through environment variables (FI_PROVIDER=efa, FI_EFA_USE_DEVICE_RDMA=1) rather than requesting the vpc.amazonaws.com/efa device.

Important framing: it is not Slinky-derived. Slinky was studied as reference only. A sibling repo (eks-slurm-on-k8s) has since been gutted into an MCP scaffolding harness — its last commit deleted 6,457 lines of manifests and scripts. And despite the name, there is no SageMaker HyperPod API integration; the coupling is naming-only.

What it has genuinely demonstrated: NCCL-over-EFA multi-node, FSDP, and hybrid Slurm↔K8s on 2×H100.
