Can we dynamically scale — and add Kubernetes nodes?

The question has two independent layers, and conflating them is what makes vendor claims confusing. Layer 1 is the Slurm-pod layer: can the number of slurmd pods change (including to zero)? Layer 2 is the node layer: can Kubernetes acquire and release actual EC2 instances underneath them? A product can do one and not the other.

Layer 1 — Slurm-pod scaling

SUNK — present but unwired

The chart has NodeSet scale-to-zero (8 references), but the open EKS recipe does not wire node autoscaling; the eksctl profile pins the nodegroup fixed.

Slinky — yes, first-class

scalingMode: StatefulSet → replicas: N↔0 including scale-to-zero, plus an HPA scale subresource on the NodeSet CRD. Or scalingMode: DaemonSet for one pod per node.

Ours — no as shipped

replicas: 2 fixed, and NodeName=slurmd-[0-1] is static in slurm.conf — the pool cannot grow without editing the config and restarting.

Layer 2 — adding Kubernetes nodes

SUNK

Budget profile pins desiredCapacity:1/maxSize:1; only one Karpenter reference in the whole repo. True node autoscaling needs the proprietary operator plus your own Karpenter/Cluster-Autoscaler.

Slinky

Karpenter. The blueprint pins slurmd to nodeSelector: karpenter.sh/nodepool: g5-nvidia, so nodes provision and deprovision on demand; the ai-on-eks base terraform already provisions P5/P5en EFA infrastructure.

Ours

None. No Karpenter, no Cluster-Autoscaler, no HPA wiring. The docs list Karpenter as future work.

Why drain-awareness is the part that matters operationally

Scaling in is the dangerous direction: if Kubernetes deletes a slurmd pod while Slurm still believes the node is allocatable, you lose running jobs. Slinky's operator drains the Slurm node before pod termination on scale-in and upgrade, and supports a PodDisruptionBudget (workloadDisruptionProtection). SUNK's equivalent behaviour is UNVERIFIED (proprietary chart), though it does enforce a related lifecycle rule for its pod scheduler (terminationGracePeriodSeconds < Slurm KillWait − 5s). Ours has no drain-aware controller — the StatefulSet uses podManagementPolicy: Parallel with anti-affinity, and nothing coordinates with slurmctld.

Verdict: Slinky YES · SUNK PARTIAL · Ours NO — on both layers as shipped.
