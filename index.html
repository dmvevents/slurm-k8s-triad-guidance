Slurm on Kubernetes: SUNK vs Slinky vs a homegrown port desk analysis

Three ways to run Slurm on Kubernetes, evaluated for an AWS P5/P5en + EFA fleet. This is a desk analysis: every claim below is tagged with the source that supports it, and the claims we could not substantiate are marked UNVERIFIED rather than guessed. The live performance arms (NCCL-at-scale, small-training comm scalability, dynamic-scale latency) are designed but not yet run — they are honestly labelled as such throughout, and no number appears on this site that was not measured.

The one-paragraph answer

Slinky is the only fully-open, production-grade option: Apache-2.0, 1,253+ commits, tagged through v1.2.1, real CRDs and controllers in-repo, brand/support by SchedMD (engineering NVIDIA-staffed since mid-Jan 2026) — and on AWS its EFA path is already solved by the official ai-on-eks blueprint, so moving to P5/P5en is a values edit rather than new plumbing. SUNK is a polished, agent-driven install experience, but the public sunk-anywhere repo is an installer/wrapper only — the operator, charts, CRDs and images are CoreWeave-proprietary and license-gated — and its open EKS recipe explicitly ships no EFA/RDMA (plain TCP NCCL, ~1/10 bandwidth by its own docs, g5.xlarge default). Treat it as a competitive/UX reference, not adoptable perf tech. Ours is the only one we fully control — and the T1 live bake-off (2× p5en/H200, same pair, same binary) split its verdict cleanly: as-shipped it is unmeasurable (the worker image carries no EFA userspace, MPI, or nccl-tests; the repo's earlier "PASS" was a TCP correctness check), but OURS-fixed — the same static manifests with a working stack — measured 477.95 GB/s busbw @8GiB under srun, 100.2% of the fabric ceiling (476.95, MPIJob), while Slinky measured 452.17 (94.8%) after root-causing a silent-TCP fallback in the DLC path. The architecture is at parity; the shipped image is the defect. Still a fixed-size, hand-operated 2-node demonstrator: no operator, no autoscaling.

What we built on top (update 2026-08-11)

The desk analysis above produced four concrete artifacts, one per gap it found. Statuses are honest: nothing below is claimed as live-verified until it has run on a cluster.

  • Ours — CLOUD/power-save autoscale (the "no dynamic scale" fix): warm floor slurmd-[0-1] + elastic slurmd-[2-15] State=CLOUD; Slurm's Suspend/ResumeProgram drive the StatefulSet scale subresource via name-scoped RBAC, tail-only scale-down. Staged as a PR on our repo; hermetic tests 6/6, not yet live — the matrix verdict stands until it is.
  • Slinky — aws/p5 vendor overlay (upstream PR, staged): the chart ships vendor overlays for google/a3ultra+a3mega and nvidia but has no aws entry, and applyVendorPatches dispatches through a hardcoded include chain — so EFA on P5 needs an upstream template PR, not a values edit. We built that overlay following the a3ultra pattern end-to-end (example values for p5.48xlarge efaCount: 32, nodeset snippet with the EFA device/hugepages/shm/env plumbing, helpers + 8 chart tests, helm-docs). Renders verified against upstream 952be03; conflict-checked against the open PR queue (#218 #204 #200 #175 #166 — zero template overlap). Awaiting filing.
  • Topology awareness: a generator that emits Slurm topology.conf (tree) plus topology.slinky.slurm.net/* node-annotation commands from real node data (28/28 tests).
  • The replicable A/B harness: six lanes behind one NCCL/EFA fabric gate — FSDP and torchtitan v0.2.2 training A/Bs (compute-bound: arms are expected to tie, bounding the scheduler tax) plus scheduler-only probes where arms genuinely differ: churn (submit→start latency), node-split (8×1-GPU concurrent), workload-split (het jobs), and elastic scale-up/down latency.

The T1 numbers on this page (477.95 / 452.17 vs ceiling 476.95) remain the only MEASURED performance rows; the harness and probes convert the rest on the next cluster window.

Three findings worth stating plainly

1. SUNK is not open-sourced

coreweave/sunk-anywhere is a one-commit Apache-2.0 installer/wrapper: docs, Helm values, validation scripts, agent "skills". No charts/, no operator Go, no CRDs, no Dockerfiles. The engine is proprietary (email sunk@coreweave.com, <COREWEAVE_HELM_REPO_URL> placeholder).

[verified: repo tree, HEAD ca81a7a3]

2. Its open EKS path has no RDMA

SUNK's own skill doc says the EKS profile "uses plain TCP for NCCL (no RDMA)… ~1/10th bandwidth… not perf benchmarks." Default GPU is g5.xlarge (A10G); p5 is opt-in and "blows budget". For a P5/P5en + EFA fleet this is the sharpest differentiator.

[verified: skills/eks/add-gpu-nodes-to-eks/SKILL.md:238; no EFA wiring in cluster-config.yaml or base/sunk-values.yaml]

3. Ours is not Slinky-derived

Our implementation is a hand-written port of Google's GKE Slurm which studied Slinky as reference only. A sibling repo has since been gutted to an MCP scaffolding harness (its last commit deleted 6,457 lines). Custom, not a fork.

[verified: local git log + grep, both repos]

Where each one wins

Slinky — openness, maturity, lifecycle automation, and a solved EFA path on AWS

Only genuinely open-source end-to-end; vendor-backed by SchedMD; real release cadence; NodeSet scale-to-zero/HPA and drain-aware lifecycle built in. The operator itself is EFA-agnostic, but AWS's ai-on-eks Slinky blueprint ships the full path (vpc.amazonaws.com/efa device + aws-ofi-nccl from the DLC on slurmd:25.11.1). Cost: newest Slurm (25.11) and K8s (1.29) floors, and the blueprint defaults to g5.8xlarge — so line-rate NCCL on P5/P5en remains the thing to measure.

SUNK — batteries-included onboarding, for CoreWeave customers, at demo grade

A polished install experience (opt-out monitoring, GPU health, SkyPilot) and EKS is validated E2E — but on A10G over plain TCP NCCL. Because the engine is license-gated it is not an open substrate a platform team can adopt or fork, and the open recipe would need the entire EFA path added to reach the P5/P5en regime.

Ours — transparency and a proven EFA multi-node + hybrid demonstrator

The only one we fully control and have actually run NCCL-over-EFA + FSDP + hybrid Slurm↔K8s on (2×H100). But: fixed-size, hand-operated, single-author, no operator, no autoscaling, no HyperPod API coupling, EFA plumbed by env-var rather than the device plugin. A demonstrator, not a product.
